# Research Runner：超时后恢复与完成后退出宽限期的比较

观察日期：2026-09-09，洛杉矶时间。运行状态最后复核到 11:10:59。本次只读检查运行中的任务、代码和日志；没有终止进程、改队列或改 runner。本文与统计明细是一次性分析成品。

结论：第二条更适合作为常态机制，即分别管理研究执行期限和成功完成后的进程退出期限。第一条适合保留为超时后的恢复兜底。两者必须使用同一套严格的成功判定，不能把 task_complete 名称或报告存在当成成功。

## 1. 样本与统计方法

扫描 logs/archive 的 21 个 JSONL 加 current.jsonl，共 22 个文件、4,580 条事件。保留日志覆盖 UTC 2026-08-19 01:03:22 至 2026-09-09 17:30:25；这是留存样本，不是系统全生命周期的完整记录。

按“Claimed ... starting formal”计数，共 804 次执行尝试：732 次 SDK 正常返回、63 次 SDK 失败、9 次没有对应返回结果。一次失败往往产生多个日志事件，统计中没有把这些重复计算为多次失败。

对 732 次 SDK 正常返回逐一使用 threadId 匹配本地会话文件，全部找到相应 task_complete。读取会话尾部最多 256 KiB，解析事件，计算：runner 的 SDK completed 时间减去会话 task_complete 时间。此差值包含完成事件传递、输出流关闭、进程退出、SDK 清理及日志记录开销，不能称作纯进程退出耗时。分位数使用排序后 floor((n-1)*p) 对应值。

最慢的正常收尾是 CRWV：会话 2026-09-08 18:52:59.029 UTC 完成，runner 18:53:10.045 UTC 返回。可复核 logs/archive/runner_2026-09-08T19-08-32-302Z.jsonl 第 26 行及统计明细中的同名样本。

63 次 SDK 失败的分类：配额不足 50 次，模型容量不足 4 次，JSON 事件解析失败 2 次，退出码 1073807364 共 7 次。没有发现 runner 的 120 分钟超时所导致的失败记录；错误文本中的其他组件 timeout 不能混作本任务超时。因此没有历史证据证明现有 120 分钟取消路径在这种故障上一定可靠，也不能称此类故障大量重复发生。

9 次没有结果的尝试中，8 次位于 9 月 9 日凌晨同一批运行末尾。按启动时间及提示中的正式输出路径逐一匹配会话，均没有 task_complete。它们不能算成“研究完成但没归档”。另 1 次是当前 CC，可明确确认成功会话终态但 SDK 尚未返回。

## 2. 必须修正的成功判定

54 次失败会话也有 task_complete：50 次配额不足、4 次模型容量不足。它们的 task_complete.payload.error 非空，last_agent_message 为空。732 次正常返回样本则全部具有无 error 的 task_complete 和非空最终答复。

因此，上一轮回答中的“有 task_complete 就检查报告并归档”需要补上成功语义。准确地说，task_complete 是本次会话执行结束，不保证任务成功。

第一条和第二条都至少需要：

1. 对应本轮 item、attempt、thread、turn，不能按公司名或最新文件模糊匹配。子任务完成不能代替根任务完成。
2. 可靠的成功终态：优先使用结构化流中的 turn.completed；若从本地会话恢复，必须检查 task_complete 无错误、最终答复存在，并且没有后续相冲突的失败或新一轮执行。最终答复仍不能单独证明报告合格。
3. 正式输出通过本轮既有校验。现有 output-validator.mjs 只检查文件路径、命名、主体、非空和修改时间；不检查章节完整性、计算正确性和研究质量。不能把文件验收说成研究质量认证。
4. 进入结束状态后，不允许同一个写入者继续改动已归档文件；必须有界地确认所属进程退出或清理完毕，再稳定验收、归档、释放并发槽。
5. 成功与失败路径只能结算一次，避免超时、完成事件、取消异常同时到达，导致先 done 后回滚。保留 token usage，避免重复累计或漏记。

原先 CC 在 09:58 的复算是研究会话自行执行的检查，本次没有重新验证研究内容；与 runner 的文件验收是不同层次。

## 3. 第一条：等总超时后再检查是否完成

触发条件仍是自开始起 120 分钟。到时先读取本轮已保存的成功证据，清理卡住的执行，再验收正式文件；满足条件则按恢复成功归档。其余情况按原来的失败处理。

优点：对正常执行路径影响较小；作为紧急补丁更容易把变化限制在超时处理；可以用持久会话补回 SDK 没交付的完成信息。

不足：整个超时前的无效等待保留。CC 09:59:01 已完成，但必须等到约 11:23:21，等待约 84 分 20 秒才开始恢复；仍占用并发槽，在有更低优先级队列时也可能拖延调度。并且当前代码是 await thread.run 后捕获异常，如果只是往 catch 塞恢复逻辑，SDK 若不响应取消，恢复逻辑根本无法运行。

所以，第一条也需要一个不依赖 SDK 自行返回的有界超时监督，以及成功/失败只结算一次的协调；实现并非完全无风险的小判断。

## 4. 第二条：收到可靠成功信号后启动单独退出宽限期

执行期保留 120 分钟上限；一旦收到本轮可靠成功终态，进入完成后退出阶段，例如最多等 120 秒。正常退出就立即验收归档；不正常退出则只清理本任务的进程，再验收、归档，并记录“成果成功、退出异常”的原因。仍未成功完成的研究不受这 120 秒影响。

优点：对 CC 这类异常，在成功完成后约 2 分钟就能处理，不必等总超时；研究慢与执行器退出慢有各自状态和耗时，便于诊断。历史 732 次正常收尾均小于 12 秒，120 秒宽限显著高于样本最大值。

120 秒是基于留存样本作出的工程建议，不是统计保证。正常任务不应人为多等 120 秒；它们依然在正常退出后立即归档。回看这批成功样本，这一阈值不会触发强制收尾，但尚未实现，不能声称运行测试通过。

不足：需要 runner 在任务执行中看到完成事件，并持久记录 thread/turn/attempt 和成功结果。当前使用 thread.run，只在全部结束后才拿结果；改为 runStreamed 后仍需要退出监督，不能只是换 API 或收到第一条 agent_message 就跳出。

当前 SDK 0.153.4 的 run 收到 turn.completed 后只保存 usage，仍继续遍历事件。底层继续等待 stdout 结束和 child exit。这解释了成功事件与 SDK 返回之间可能存在分离，但不足以定位 CC 卡在具体哪一步。

本次 CC 的直接证据来自本地会话 task_complete；没有保存其原始 SDK stdout，因此不能断言 SDK 一定已经收到了 turn.completed。若第二条只监听 stdout，可能漏掉成功事件仅落在会话里的情况。实际实施应考虑按已确认 thread/turn 轻量核对本地会话成功终态，或保留第一条作为恢复兜底。不能每秒全盘扫描所有历史会话。

发出取消会使 SDK 抛异常。已经确认研究成功且产物通过验收时，应将主动取消产生的退出异常归入收尾异常，不能再掉进原来的失败回滚分支；但也不能把所有其他真实错误统一吞掉。

## 6. 建议选择与实施验证边界

如果只能选一个作为长期主方案，选择第二条。它处理的是执行生命周期的混淆，历史正常收尾延迟提供了较明确的阈值依据。第一条可作为恢复兜底，或时间紧迫时先实施的过渡补丁；它不能解决长时间占槽等待。

第二条不应扩张为新的研究质量评审器：沿用正式输出契约，改善的是成功证据、进程退出和结算原子性。内容质量规则是否增强应另行决定。

实施前应验证：成功终态后进程挂住；有报告但尚未完成；task_complete 带 error；取消不返回；成功与总超时同时到达；主动清理不能触发报告回滚；错误的旧会话和子任务不能误关联；缺文件或旧文件必须拒绝恢复；正常成功任务继续及时退出。需要可控的模拟子进程与故障注入，不宜拿正在运行的生产任务试杀。

可复核代码：runner.mjs 的 runCodex 和 runOneQueueItem；node_modules/@openai/codex-sdk/dist/index.js 的 run、runStreamedInternal、CodexExec.run；validators/output-validator.mjs；domains/output-backup.mjs；queue-store.mjs 的 markQueueItemFailure。

官方文档说明 JSONL 流区分 turn.completed、turn.failed、error 等事件：[Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)。本机的具体退出等待行为以已安装 SDK 0.153.4 代码为依据。

逐项 threadId、会话路径、runner 日志路径与行号、完成时间和延迟见同目录“统计明细.json”。该文件保留 795 个已返回尝试的明细及 9 个未返回尝试的启动证据。
