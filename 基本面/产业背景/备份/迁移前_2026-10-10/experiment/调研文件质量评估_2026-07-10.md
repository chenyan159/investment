## 二、评估边界与适用限制

本次评估回答的是：

- 文件有没有清晰的研究命题、边界和定义；
- 来源在文档内部是否足够权威、丰富、可定位；
- 数字和表格能否内部勾稽；
- 模型、参数、公式和情景是否可复算；
- 推理是否把 CapEx、MW、订单、交付、收入和利润正确串联；
- 风险是否能被定量证伪并持续更新；
- 报告是否能支持实际研究决策。

本次评估**不回答**：

- 外部链接是否仍可访问；
- 引用页面是否真的包含报告所写数字；
- 2026 年公司数据、项目状态和股价是否真实无误；
- 报告预测是否会实现。

因此，90 分以上表示“文档内部研究质量高、接近可审计”，不等于“外部事实已经核验”或“预测正确”。在完成外部事实核验、算术自动检查和跨版本参数统一之前，5 份文件都不应被视为最终投资事实库。

### 3.1 评分方法

共 8 个评估方面，每方面 6 个指标，共 48 项。每项按 0—5 分评分：

| 分数 | 含义 |
|---:|---|
| 5 | 完整、明确、内部一致，接近可审计或可直接维护 |
| 4 | 较强，仅有局部缺口，不妨碍主要使用 |
| 3 | 基本可用，但存在实质缺口，需要人工判断 |
| 2 | 较弱，关键环节缺失或证据不足 |
| 1 | 仅略有涉及，不能支撑判断 |
| 0 | 完全缺失或明显错误 |

总分计算：`48 项得分之和 ÷ 240 × 100`。八个方面等权，每方面占总分 `12.5%`。

| 百分制 | 解释 |
|---:|---|
| 90—100 | 高质量研究稿，接近可审计；仍需通过事实核验门槛 |

| 60—69.9 | 信息型初稿，适合提供线索，不适合直接决策 |
| 低于 60 | 结构或证据不足，不应作为正式研究依据 |

### 6.1 `sol_max`：最佳主底稿候选

文件：`行业调研_AI数据中心建设规模与产业链订单映射_sol_max_2026-07-10.md`

**总体判断：**五份中最完整、最接近可维护研究底稿。优势不是篇幅，而是形成了“范围—账本—模型—物理量—订单池—公司—风险—更新”的闭环。适合成为唯一主模型，但修复前仍不能称为完全可审计。

主要优点：

1. 第 3—8 行把报告日、版本、数据截止、估值快照和研究属性一次写清。
2. 第 71—79 行建立客户直接 CapEx、供应链穿透订单、诱发型上游订单三个账本，明确哪些能加总。
3. 第 83—94 行给总量、IT load、energized load 和加速器等效量公式；第 895—919 行给参数、更新频率和复核样例。
4. 第 187—266 行用美元/MW、rack、GPU、用电、PUE、项目周期和外部市场数据做交叉验证。
5. 第 329—547 行的产业链订单池不仅列规模，还列确认节点、单位经济、公司、毛利属性和验证指标。
6. 第 742—798 行把反证阈值、概率/影响、模型动作、跟踪频率和更新模板连成闭环。
7. 第 921—928 行提供审计规则，是五份中维护性最好的版本。

主要缺点：

1. **单位数量级错误：**第 43 行写 facility 约 `$9-14B/MW`，而第 180、185、491 行均为 `$9-14M/MW`，前者高了 1,000 倍。
2. **总量仍不可完整复跑：**第 139、913 行称相关变量经“成组抽样后裁剪”，但没有相关矩阵、抽样规则、随机种子或可执行参数表，`$410-470B` 只能理解，不能独立重算。
3. **来源日期冲突：**第 367 行把 Bloom/Oracle 披露日写为 `2026-06-24`，R45（第 880 行）写 `2026-04-13`。
4. **来源定位仍不够细：**R 编号能追到网页，但没有页码、章节、表格或原文摘录；综合区间常由一组来源共同支撑，不能一对一审计。
5. **公司归因仍偏定性：**公司映射很广，但多数没有从行业订单池桥接到“公司可获得收入、利润、现金流和美国 AI 占比”。
6. **过长：**932 行、64 张表，母项、子集、穿透值和诱发订单虽有提示，普通读者仍容易误加总。

建议角色：修正 P0 错误后，以它作为唯一主底稿；其他版本只做挑战模型和摘要，不再并列维护五套总量。

## 七、跨文件一致性审计

### 7.1 同一指标存在版本冲突

以下只说明文件之间不一致，不判断哪一个外部事实正确：

| 指标 | 文件内不同写法 | 质量影响 |
|---|---|---|
| Alphabet 2026 CapEx | `baseline_05-22`、`sol_max` 为 `$180-190B`；`luna_max`、`sol_xhigh`、`terra_max` 为 `$175-185B` | 同日新稿仍未统一“最新指引”版本 |

| Eaton backlog 增速 | `luna_max` 为 `48%`；`sol_max`、`sol_xhigh` 为 `44%` | 可能是分部/滚动口径差异，需显式标注 |

| Amazon Q1 披露日 | 部分文件写 2026-04-29，`sol_max` 来源表写 2026-04-30 | 需统一时区与披露日规则 |

### 7.2 相同名词背后并非相同物理口径

各文件都使用“AI IT load”，但实际含义不同：

- `baseline_05-22` 主要是由全栈 CapEx 反推的订单容量；
- `luna_max` 是当年采购、开工、交付和部分投产对应的建设转化量；
- `sol_max` 同时区分“支出对应 load”和“energized load”；
- `terra_max` 区分“深度开工/签约 load”和“实际通电 load”；
- `sol_xhigh` 在不同段落中更接近建设/energization 混合口径。

因此，不能直接把五份报告的 GW 数字放在一张图里比较，除非先统一成 `planned / contracted / requirements-met / under-construction / energized / accepted` 六个状态。

### 7.3 共性方法缺口

四份新稿虽然都比基准稿成熟，但仍有六个共同问题：

1. 核心总量依赖未直接披露的 `AI 占比 × 美国占比 × 当年转化率`；没有一份给出完整、可运行、含相关性的参数模型。
2. “区间端点不能机械相加”多次被用来解释不闭合，但没有明确端点配对、相关矩阵或抽样方法。
3. 客户直接 CapEx、供应商 gross invoice、BOM 穿透价值和诱发型上游 CapEx 虽有概念区分，实际表格仍存在交叉和口径漂移。
4. R 编号最多追到网页，普遍缺页码、段落、表格、原文短摘录和访问快照。
5. 行业订单池到公司收入/利润/现金流的桥接不足，容易把“行业受益”误读成“股票受益”。
6. 四套同日模型并列存在，却没有明确主模型、挑战模型、版本差异和变更日志，形成模型选择风险。

## 八、改进优先级

### P0：先修复已发现的确定性错误

| 文件 | 必修项 |
|---|---|
| `sol_max` | 把第 43 行 `$B/MW` 改为 `$M/MW`；统一 Bloom/Oracle 日期；公开成组抽样/裁剪规则 |
| `terra_max` | 重做第六、七节订单池勾稽；明确工程/REIT/utility EPC 重叠；修复反向百分比区间 |
| `luna_max` | 给客户级过滤参数；让 CapEx 模块表与总量闭合；正文增加 R 编号 |
| `sol_xhigh` | 修复 Supermicro 引用、Bloom 状态、整机/compute 口径、模块残差和 rack/MW 相关性；删除或补全股价来源 |
| `baseline_05-22` | 不建议继续局部修补；保留历史版本即可 |

### P1：建立统一的三层账本

未来只维护三个明确分离的账本：

1. **A 层：客户直接建设 CapEx**——可加总，用于回答美国当年到底投入多少。
2. **B 层：供应链穿透价值**——GPU、HBM、CoWoS、整机、网络等母项/子项，只用于价值分配，不跨层相加。
3. **C 层：诱发型上游 CapEx**——WFE、测试、材料和扩产，明确滞后期，不计入客户直接建设总额。

每个数字必须带 `ledger=A/B/C`、`additive=yes/no`、`parent_claim_id` 和 `recognition_stage`。

### P2：把报告变成可运行模型，而不是只有公式说明

每个核心结果应能由下列字段重算：

```text
Claim ID
来源 ID / 页码 / 段落 / 访问日
事实值或估算值
地理范围
期间
币种与单位
情景
参数低值 / 基准 / 高值
参数选择依据
相关性或端点配对规则
公式
是否可加总
置信度
反证阈值
```

至少增加四类自动检查：

- 单位检查：`B/MW`、`M/MW`、`GW`、`MW`；
- 区间检查：低值不得高于高值，百分比方向必须一致；
- 闭合检查：模块和、母项/子项、穿透层、残差；
- 引用检查：正文 R 编号必须存在，关键数字必须带来源或明确标注“模型估算”。

### P3：确立单一主模型和文档角色

建议目录角色如下：

| 角色 | 建议文件 |
|---|---|
| 主模型 / 审计母版 | 修订后的 `sol_max` |
| 独立挑战模型 | 修订后的 `terra_max` |
| 公司订单证据库 | `luna_max` 中的公司级证据表 |
| 2—3 页执行摘要 | 修订后的 `sol_xhigh`，但不再维护独立总量 |
| 历史基线 | `baseline_05-22` |

主模型和挑战模型之间必须增加一张“差异桥接表”，至少解释：五大客户 CapEx、AI 占比、美国占比、转化率、NeoCloud/AI Factory 增量、租赁去重、单位 MW 成本和 energized MW。

### P4：外部事实核验门槛

在任何文件升级为正式投资底稿前，至少通过四个门槛：

1. 所有核心链接可访问，引用数字能在原文定位；
2. 所有核心数字都有截止日和访问快照；
3. 算术、区间、单位和跨表勾稽自动检查全部通过；
4. 跨文件关键输入冲突已经解决并留有变更记录。

当前 5 份文件均未通过完整的外部事实核验门槛。

## 九、最终判断

这批实验文件已经证明：高质量的产业链研究不能只靠“更多资料”和“更长报告”，而要靠统一账本、可复算参数、严格引用和模型治理。

若只选一份继续维护，应选择 `sol_max`；若保留第二份，应将 `terra_max` 明确定位为挑战模型。`luna_max` 的公司订单证据值得并入主模型，`sol_xhigh` 应压缩成不维护独立数字的执行摘要，`baseline_05-22` 则保留为历史版本。

最优升级顺序是：**先修 P0 确定性错误 → 统一三层账本 → 建可运行参数模型 → 建正文 Claim ID 与来源定位 → 再做外部事实核验。**
